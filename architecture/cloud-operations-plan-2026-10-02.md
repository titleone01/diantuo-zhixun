# 电拓智训服务器运营与迁移规划

规划日期：2026-10-02。适用范围：用户主要在中国大陆，近期邀请少量学员试用，最多约 50 人同时在线；先完善项目，再实施迁移。用户随后补充学校有可全天运行的电脑，且校内和校外都需要访问，因此新增学校自有电脑方案。

当前建议先验证学校现有电脑与校园网能否满足长期运行和校外访问条件，再决定是否购买云服务器。学校方案建议使用专用 4 核及以上电脑、16GB 内存、256–512GB SSD 和千兆有线网络；8GB 内存也可先试运行。云端方案保留作备选：小规模试用全年现金预算约 1300–1700 元，经常 50 人集中开课约 2000–2400 元。两条路线均应建设正式生产服务、异机备份及版本化发布。

这是规划与只读审查结果。本次没有购买服务、迁移数据、更换域名、重启服务或部署公网；50 人容量、恢复时间和新云端兼容性均待实测。工程工作量为估算，不是工期承诺。

## 学校电脑替代云服务器

学校已有可全天开机的电脑时，自有设备承载当前网站在技术上可行，值得优先试验。服务器仍负责登录、图纸、保存和评测，学员端负责画布与实时仿真。现在没有学校设备参数、校园出口实测与网络管理要求，因此本节是配置建议，尚未确认任何一台学校电脑已可承载 50 人。

用户选择目标电脑优先使用 Windows，后续按需要再调整。保持当前版本和域名的具体换机步骤、迁移清单与数据验收标准见 [电脑间迁移与验收流程](computer-migration-runbook.md)。

### 硬件配置建议

| 项目 | 可先试运行 | 长期运行建议 |
| --- | --- | --- |
| CPU | 常规桌面级 4 个物理核，具体性能需看型号 | 4–6 个物理核及以上的办公电脑 CPU |
| 内存 | 8GB，尽量专用 | 16GB，给系统、数据库、上传与维护留余量 |
| 硬盘 | 健康的 256GB SSD，至少留 60GB 空闲 | 256–512GB SSD，留约 100GB 空闲，并有另一设备存备份 |
| 显卡 | 集成显卡即可 | 不需要为服务器增加独立显卡 |
| 网卡 | 千兆有线网卡 | 稳定有线连接，固定内网地址由学校管理方分配 |
| 运行条件 | 稳定供电、散热良好 | 专用机器、自动恢复服务；如有现成 UPS 可接入 |

学校电脑建议 8–16GB 内存，是因为桌面操作系统、学校管理软件及可能的办公任务要占资源，与前述 Linux 云服务器 4GB 起步并不矛盾。若只能共用办公电脑，优先 16GB，并测试办公高峰时是否影响网站；不能按“空闲时很快”判断课堂可靠性。不要只看 i3/i5/i7 标签，具体代际、核数和硬盘健康更有意义。

50 人并发的验收场景仍采用本规划末尾的集中登录、打开图纸、保存和评测。增加服务器配置不能解决学员电脑浏览器渲染慢的问题。

### 校内和校外访问

首选由学校信息中心提供或确认已有网站托管环境、虚拟机、公网 HTTPS 入口或反向代理。如果学校已经有这些资源，使用其统一入口通常比单独维护桌面电脑的对外链路更方便。实际能否免费分配资源与使用 `.com` 域名，需要学校确认，不能默认学校现有网站备案自动覆盖新域名。

若使用指定电脑，校园内访问可通过学校管理的 HTTPS 内网入口到这台电脑；校外访问优先经过学校已有公网入口。应用继续在受控环境运行，不把开发端口 3000 直接暴露公网。条件允许时，可由学校配置同一域名在内外网走对应路径，避免机房上课也绕行外网；这需要网络管理方实施，并非现有功能。

如果学校没有可用的公网入口，可以评估现有 Cloudflare Tunnel。它通过电脑主动向外建立连接，不要求电脑拥有可被公网直接访问的 IP；但是校园防火墙必须允许相关出站连接，且应符合学校网络管理要求。[Cloudflare Tunnel 官方说明](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)

沿用隧道可以降低试迁移改动，但不会因服务器从笔记本换成学校电脑而自动改善大陆网络体验。必须从学校宽带、手机流量和校外其他运营商测试；学校不允许隧道时，应使用信息中心提供的入口，不能通过绕过其限制来部署。隧道也不能作为免除公网服务相关备案要求的依据。

网络指标要分开看：千兆网卡是电脑到校园网的链路；校外学员加载图纸消耗的是学校实际可用的公网上传能力。对于经常 50 人集中打开页面的情况，建议先以可稳定获得 20Mbps 以上上传能力进行测试，能获得约 50Mbps 余量更好；这是测试选型目标，不是容量保证。若低于 10Mbps，应重点测首屏峰值，并优化缓存和静态资源分发。宣传的“千兆宽带”或下载测速不能代替上传和高峰实测。

学校网络还要核实晚间、周末与寒暑假是否断网，认证是否必须每天在浏览器重新登录，以及固定 IP、跨楼栋访问与校园出口策略。机房有线网络通畅，并不等于校外已经可访问。

### 学校设备的持久化与无人值守

学校机房可能安装还原卡、重启恢复或统一镜像系统。数据库、附件、证书和服务配置必须由管理员放在明确不会被还原的位置，并验证重启后数据仍在。不同分区不一定意味着不受还原，不能仅凭盘符判断。

目标运行方式是电脑通电启动后，应用和网络入口自动恢复，不需要有人登录桌面或双击快捷方式。当前项目的 Windows 桌面启动器仍需要手动执行，尚不满足该目标。Cloudflare 官方支持将 `cloudflared` 安装为 Windows 系统服务，但应用本身也需要对应的服务管理与健康检查。[Windows 隧道服务文档](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/as-a-service/windows/)

长期设置应包括不休眠、系统更新维护窗口、来电自动开机（设备支持时）、异常退出后重启，以及明确的故障联系人。短时 UPS 主要用于应对短停电和安全关机；若交换机、路由器或整个校园出口断电，单独给电脑供电并不能保证外网访问。

### 电费与新增支出

若电脑和校园网络已有且无需增购，服务器租金可省下。学校承担电费仍然是实际成本，应区分“用户新增付款”和“学校整体运行成本”。

全年电量计算：平均实测功耗 W ÷ 1000 × 24 × 365。下表假设电价为 0.8 元每度，仅用于计算，不代表学校实际电价；显示器关闭，网络设备与 UPS 损耗未单列。

| 主机平均功耗假设 | 全年电量 | 示例全年电费 |
| --- | --- | --- |
| 20W | 175.2 度 | 约 140 元 |
| 50W | 438 度 | 约 350 元 |
| 100W | 876 度 | 约 701 元 |

不要用电源的 300W/500W 额定功率代替平均功耗，应在设备运行实际网站时测量。若电脑原本就全天开机且继续做原有工作，仅新增负载部分才算增量用电；若原本会关机、现在为网站全天开启，则应计算增加的运行时段和整机功耗。

其他费用仍包括普通 `.com` 域名约 80–120 元/年预算、备份及可选硬件。已有 NAS 或另一台受管理电脑时可利用其存放加密备份，但需隔离权限和保留历史版本；若另购云备份，沿用 120–360 元/年预留。已有设备全部复用、入口无额外收费、备份资源足够时，新增年度付款可能主要是域名；这不等于没有维护与故障成本。需要新买 UPS、SSD 或备份盘时另计一次性支出，本次未询价。

### 建议实施顺序

1. 收集候选电脑的 CPU 型号、内存、磁盘与系统信息，同时由学校确认是否存在还原系统、全天供电网络和可用公网入口。已有机器先评估，不先购买新电脑。
2. 在学校电脑建立独立测试副本，校内先验功能，再从校外验证入口与高峰速度；不让它与笔记本同时通过同一个生产隧道接收独立数据库写入。
3. 若先沿用受支持的 Windows 系统和现有运行时，可安排约 1–2 个工程日做迁移演练、服务自启与备份验证，再观察 3–7 天网络情况。此为估算，学校网络处理时间另计；现有 `wrangler dev` 仍只作为过渡试运行。
4. 长期运行采用本规划的生产 Node 服务、持久化数据库、私有附件及版本发布能力。专用电脑适合考虑 Linux；如果学校要求保留 Windows，也可另行建设正式 Node 服务和服务管理，不必为了试运行立即重装系统。生产适配仍按约 4–7 个工程日估算，可复用于未来迁云。
5. 在同一真实校园出口下完成 50 人、同教室共享 IP、服务器重启、断网恢复和备份还原测试。确保课后及周末可从校外访问，再切正式流量。
6. 迁移时先停笔记本旧站写入、完成最终复制、核对后切换唯一入口。可以先保留原域名完成换机，稳定后再单独换 `.com`，减少一次同时变更的因素；原域名保持不变时，已有浏览器本地恢复记录的 origin 也保持不变。

学校方案的优先级取决于“已有专用设备、网络入口可靠、有人维护”三项是否成立。满足时可先承担试运营并省下云租金；若校园出口或假期运行不可保障，再回到云服务器方案。后续身份、域名与备案安排应依据实际运营主体确定，不能因为使用学校电脑就自动认定属于学校主体，也不能照搬前文个人备案假设。

## 为什么 50 人要关注带宽

在线人数只说明多少人同时使用，不能直接换算成服务器配置。当前持续运行的电气仿真主要消耗学员设备性能，后台压力集中在登录、打开图纸、保存、发布与服务端评测。当前未发现聊天长轮询功能，100ms 的仿真定时器也不是 API 轮询。

容量规划假设：没有视频直播、云端 AI 推理和多人实时共同编辑；学员不会持续同时上传大文件。当前教学视频由浏览器访问外部视频地址，不计入本服务器视频出站；未来若改为自托管视频，需要单列存储、转码与分发成本。新增上述功能时重新估算。

一个用于解释带宽的假设：若每人首次需要下载 2MB 资源，50 人集中打开就是 100MB。全部由单机出口发送，忽略协议开销，6Mbps 至少约需 133 秒才能送完这一批数据，10Mbps 也至少约需 80 秒。这不是当前网页实测加载时间，但说明增加 CPU 不一定解决集中首载。

因此迁移前应加入压缩、带哈希静态资源的长期缓存、按需加载、清理构建产物和课前预加载，并实测冷缓存首屏。如果仍达不到目标，优先使用已备案的国内静态资源 CDN 或调整带宽，再考虑加 CPU。公开前端资源可分发；成员私有图纸仍须鉴权，不能为了缓存速度改成公开桶。

用于初始流量预算的示例：每天 50 名学员，每人 50MB，30 天约 75GB/月；每天 200 名学员则约 300GB/月。这里的 50MB 是预算假设，须用试运营流量修正。峰值 50 人在线并不能确定月活、访问次数与月流量。

Cloudflare 官方 Workers 付费计划包含每月 1000 万次请求和 3000 万 CPU 毫秒等额度；费用随实际用量变化。它按调用计费，不按传统服务器核数采购。[Workers 价格](https://developers.cloudflare.com/workers/platform/pricing/)

D1 付费计划包含一定读写量和 5GB 存储；R2 Standard 有每月 10GB-month 免费存储额度及操作额度，R2 直接出网不收传输费，但 Worker 调用和其他连接服务可能计费。不能仅因数据小就承诺总账单永远是 US$5。[D1 价格](https://developers.cloudflare.com/d1/platform/pricing/)；[R2 价格](https://developers.cloudflare.com/r2/pricing/)

Cloudflare 普通全球套餐不等于中国大陆网络套餐；China Network 是 Enterprise 的独立订阅，并有接入条件。结合用户主要在大陆，低单价不足以让它成为本项目默认首选。[Cloudflare China Network](https://developers.cloudflare.com/china-network/)

当前项目尚在完善，没有迫切停掉笔记本的期限，建议先验证学校方案；若最终选择租云服务器，可直接准备大陆生产版本，避免为了短暂过渡反复迁移数据。备案主体按实际运营方确定，条件不满足时再根据真实运营范围选择适用主体或部署路线。

## 推荐的生产结构

```text
学员浏览器
    │ HTTPS，正式 .com 域名
    ▼
大陆服务器 Caddy
    ├── 前端静态文件，压缩与浏览器缓存
    └── Node 生产 API，邀请登录与权限检查
            ├── SQLite 持久化数据库
            └── 私有图纸持久化目录

数据库一致性备份及图纸副本 ──► 另一存储服务的私有备份桶
笔记本用于开发和发布；关机后不影响线上运行
```

先采用单机单应用实例，业务数据放在容器外的持久化卷。SQLite 采用 WAL、合理的忙等待、短事务与索引，适合先验证当前短小写入场景。保留存储接口以便后续切换私有 COS/OSS；暂不因 50 人在线就购买独立数据库、Redis、负载均衡或 Kubernetes。

数据库最终选型以实际并发写入测试为准。若评测或保存产生明显写锁等待，或将来要多台应用服务器，再迁移 PostgreSQL。应用实例复制、自动扩容和单机 SQLite 文件不能直接组合成多机高可用。

Caddy 用于 HTTPS 入口，自动证书能力可减少人工续期；证书状态也应持久保存并监控有效期。[Caddy HTTPS 文档](https://caddyserver.com/docs/automatic-https)。Docker Compose 可用于单服务器生产部署，需配置重启策略、健康检查和生产环境参数。[Docker 官方生产部署文档](https://docs.docker.com/compose/how-tos/production/)

## 完善项目时应提前做的改造

1. 增加正式 Node HTTP 入口，保留现有二维引擎、API 行为与旧三维资产。生产启动不依赖 Wrangler 开发服务器，也不依赖 Windows 桌面脚本。
2. 将数据库访问抽成可替换接口，把 D1 的 `prepare/bind/first/all/run/batch` 及返回元数据语义映射到 SQLite。`batch` 必须保留事务原子性，不能改为无事务的逐条循环。Better Auth 的 Drizzle D1 驱动一并替换，保持密码哈希兼容、一次性邀请原子消费、版本冲突检测和外键约束。
3. 将 R2 的读取、上传和删除改为私有存储适配器，保留对象键、类型、字节数及引用关系，保留授权后的 Range 分段读取以支持 PDF 浏览等场景。业务文件不放 `public/` 或容器临时层。
4. 修正反向代理与真实 IP 处理。当前限流读取 `cf-connecting-ip`，普通服务器环境不能继续依赖这一字段，也不能无条件相信客户端伪造的转发头。测试整班共用一个公网 IP 的登录与邀请注册，避免误触限流。
5. 控制上传大小与并发。当前单文件上限 20MiB，并有整文件缓冲处理；不能用“50 人在线”推断能承受 50 个最大文件同时上传。
6. 域名、数据库、文件目录和认证秘密都通过环境配置，区分开发、测试与生产。管理员初始化通过受控部署流程完成，正式公网禁止开放初始化入口。
7. 加入数据导出、恢复、迁移核对及发布脚本，建立独立健康检查。静态演示 `docs/` 不作为成员站生产产物；继续遵守项目既有构建要求。

## 部署与后续升级

目标流程：本地修改 → 自动测试 → 生成版本化发布包或镜像 → 测试环境验证 → 一次发布操作 → 健康检查与登录保存回读 → 保留上一版以便回退。

建议使用 Git 仓库与 CI 构建，镜像使用不可变版本标签或提交编号。大陆服务器从可稳定拉取的镜像仓库取产物；不要把每次发布都能直连海外镜像仓库当作前提，可准备国内仓库或受控上传发布包。私密环境变量、账号数据和图纸不进 Git 或镜像。

发布前备份数据库，数据库变更先做兼容扩展，再切新版本；删除旧列等破坏性变更延后。软件回退只切回上一版镜像，不能自动解决已经发生的数据库破坏。数据库恢复涉及恢复点之后的数据丢失，应单独判断和执行。

单机初期可以接受计划维护窗口，常规更新预留约 1–5 分钟短暂不可用，不承诺零停机。流程建立后，一次普通版本发布可按 10–30 分钟人工检查时间规划，自动构建耗时另计；常规维护预留每月 1–2 小时，包含补丁、告警、备份和账单检查，功能开发不计入。

初始备份建议为每小时生成一个完整恢复点：先用 SQLite 在线备份机制或受控停写取得一致性数据库快照，从快照生成附件引用清单，再异机复制清单中新增的不可变附件；快照、清单和所需附件全部核对完成后，才能把该恢复点标记为可恢复。每天做全量清单校验，每次发版前再建立完整恢复点。保留最近 48 小时的小时恢复点、7 天日恢复点及 4 周周恢复点，文件延迟清理，所有保留恢复点引用的附件都须保留。运行时仅复制一个 SQLite 文件会漏掉 WAL。

恢复目标以最近完整恢复点计算，暂定数据最多回退约 1 小时加当次备份耗时、确认故障后约 2 小时内恢复；这些是规划目标，需恢复演练验证。不能用“数据库每小时备份、图纸每天备份”承诺完整数据只丢 1 小时。备份失败必须被监测，且每月至少做一次抽样恢复；同一块云盘内的副本不足以应对整机丢失。

## 正式域名与备案安排

`.com` 的作用是建立长期入口和品牌，不会自动提高访问速度或网站稳定性。建议在支持大陆备案的注册商购买普通英文 `.com`，使用本人实名认证和本人控制的账号，核对域名持有人与备案主体的一致性，设置自动续费。若已有满意名称，可先查询可用性再注册；本规划没有查验或购买具体名称。

若仍由个人实际运营并邀请试用，应先把真实首页、课程和作品交流功能，以及“个人开发电气仿真工具，邀请少量用户免费试用”的说明交给接入方备案专员，核实本省是否支持个人主体；免费、邀请制不保证个人备案一定通过。若属于学校正式业务，则按学校实际主体与信息中心流程处理。腾讯个人网站要求限制企业、团体、论坛及需前置审批的内容，成员交流功能的具体归类需确认。不能只凭“学习工具”断言需要教育审批，也不能仅改名字掩盖实际运营范围。[腾讯个人网站信息要求](https://cloud.tencent.com/document/product/243/19644)；[阿里云备案类型选择](https://help.aliyun.com/zh/icp-filing/how-to-choose-the-record-type)

大陆服务器对外服务前应完成 ICP 备案，域名注册本身不等于备案通过。阿里云个人备案流程给出的预计时间为 3–22 个工作日，本项目排期预留约 2–5 周；材料补正或假期会延长。上线后按要求办理公安联网备案。[个人网站备案流程](https://help.aliyun.com/zh/icp-filing/basic-icp-service/getting-started/quick-start-for-icp-filing-for-personal-websites)

域名注册、备案、生产适配可并行进行。后续若开展收费培训、商业运营或扩大公开交流，应重新核对真实运营范围和主体资格；这部分未计入当前个人试用方案。

## 迁移顺序与时间安排

| 阶段 | 主要工作 | 预计投入或等待 |
| --- | --- | --- |
| 准备 | 确认个人备案可行性、选域名、选有备案资格的服务器 | 用户配合约 1–3 小时，材料反馈另计 |
| 生产适配 | Node 入口、数据库与附件适配、环境配置、限流修正 | 工程约 2–3 天 |
| 部署工具 | Docker、HTTPS、版本发布、备份与监控 | 工程约 1–2 天 |
| 迁移演练及压测 | 数据核对、两账号权限、50 人负载、恢复演练 | 工程约 1–2 天 |
| 备案 | 实名、材料、核验与审核，与技术工作并行 | 规划约 2–5 周 |
| 正式切换 | 停写、最终复制、回读、改入口和观察 | 先预留 30–60 分钟维护窗口，按演练修订 |

工程合计约 4–7 个专注工作日，按单人熟悉项目、当前功能规模估算，不包含新功能开发与无法预见的兼容问题。保守可安排 1–2 周技术工作，与备案等待重叠。

正式迁移按以下顺序执行：

1. 在独立测试环境演练一次全量迁移，用数量、哈希和关联关系核对账号、草稿、发布快照、评测和图纸；不得只迁 20 张课程原图而遗漏学员附件及历史快照。
2. 切换前提醒所有试用者将旧域名浏览器内未同步的接线保存到服务器或导出。必要时提供旧页面的导出窗口，不能先强制跳转导致恢复记录无法取出。
3. 正式维护时停止旧站写入，制作一致性最终备份，导入新站；旧站与新站不得各自接受独立写入。
4. 保留账号标识、密码哈希、对象键、图纸元数据、课程关联和并发版本信息。换域名后安排重新登录，旧域名 Cookie 不会自然变成新域名会话。
5. 验证 `.com` 下的 HTTPS、认证来源白名单、邀请链接、登录、保存、权限与图纸访问，再开放服务。新站必须完全不依赖笔记本或旧 Tunnel。
6. 保留本机离线恢复副本 1–2 周，保留旧域名 30–90 天；确认浏览器草稿处理完成后，通过独立云端规则将旧地址引导至新站，不能继续依赖笔记本提供跳转。
7. 切换后若新站已产生数据，回退前先停写并导出新增变化。直接把域名指回旧数据库会丢掉新站数据，不能作为默认回退操作。

D1 官方支持 SQL 导出/导入，但运行时状态目录不是可直接上传到云服务的通用备份包，需按目标数据库处理兼容性；R2 本机对象也需按对象内容及元数据迁移。[D1 导入导出文档](https://developers.cloudflare.com/d1/best-practices/import-export-data/)

## 迁移验收与扩容依据

上线前执行项目约定的 `npm run typecheck`、`node --test tests/*.test.mjs`、`npm run build`、`npm run build:pages`，再对实际生产产物做后台与浏览器验收。当前 `npm run build:local` 是本地完整站产物路径，生产构建需有单独且已验证的入口，不能用静态 Pages 成功替代后台通过。

容量验收拟定为 50 个独立账号持续约 30 分钟，另加 75–100 个虚拟用户短时余量测试；只在授权的测试环境运行。场景包括集中登录、冷缓存打开课程与图纸、同一校园 NAT、保存与评测、有限并发上传。API 压测和真实浏览器加载分别验证，API 请求成功不代表页面已可操作。

初始验收目标：常规读取及保存 API 的 P95 小于 1 秒，较重评测小于 3 秒，异常服务端错误率低于 1%，保存丢失和越权读取为零；典型设备热缓存主要页面 3 秒内可操作，50 人冷启动以 10 秒内可操作作为优化目标。上述均是待验证目标，若带宽不足就优化分发或升带宽，不能直接宣称达标。

同时完成真实二维端子拖线，核对移动、缩放、重载后世界端点一致，验证十门课程行为与两个账号的私有草稿、图纸隔离。云服务器重启后自动恢复服务；做一次恢复演练，并在笔记本关机后从手机流量及不同宽带访问验证。

扩容由监测触发：持续 CPU 接近 70%–80% 且确认是计算瓶颈时升 CPU；内存持续接近 80% 或发生内存不足时升内存；出口持续饱和则先提高带宽或分发静态资源；数据库锁等待则优化写入、索引或更换数据库；磁盘使用到约 70% 时处理日志与备份保留或扩盘。单一百分比不自动等同于必须扩容，需结合响应时间定位。

当前最值得先完成的是生产运行适配、草稿导出与数据恢复、可重复发布流程以及个人备案可行性确认。项目完善期间把这些能力一起建设，迁移时就可以使用已经演练过的流程。
