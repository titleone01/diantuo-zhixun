# 电拓智训电脑间迁移与验收流程

编制日期：2026-10-02。目标是将笔记本上的现有成员站迁移到另一台电脑，完整保留已保存账号、草稿、作品、图纸和权限，并沿用现有域名及 Cloudflare Tunnel。本文是待实施流程，本次仅核对源码，尚未备份业务数据、停止服务、连接目标电脑或实际迁移。

## 迁移范围

先只更换承载电脑，固定同一套代码、依赖和域名；稳定后再单独升级软件、改为正式生产运行方式或更换 `.com`。用户已选择优先使用 Windows，保留以后调整系统的可能，因此当前按 Windows 到 Windows、相同运行时版本规划。若将来改为 Linux 或普通 Node 加 SQLite 服务，需另行验证运行时及存储适配，不承诺原样复制内部状态目录即可上线。

本次终端核对到 Node v24.16.0、npm 11.13.0；实际迁移时应复核正在运行服务使用的 Node、Wrangler、workerd 和 cloudflared 版本，而不是只以终端默认版本判断。依赖由当前 `package-lock.json` 固定，记录代码提交及全部未提交修改。

“无损”的验收对象是约定范围内的数据内容及关联关系，允许安排短暂停服。浏览器里尚未提交的接线必须先保存或导出；用户可能需要重新登录。不能把未保存的浏览器状态、登录体验不变和服务器数据完整混为一谈。

## 必须迁移的内容

| 内容 | 当前项目位置或来源 | 处理方式 |
| --- | --- | --- |
| 当前完整代码与素材 | 项目源码、public、shared、db、scripts、配置、package.json、package-lock.json | 保留现有修改及旧三维代码、模型；仅从 Git 拉取不能保证包含未提交文件 |
| 账号和全部业务数据、私有图纸 | `.wrangler/state/` | 停止全部写入后整体保存，包含 D1、R2、对象内容、元数据及现存 WAL 等辅助文件，保持相对目录结构 |
| 认证与站点配置 | `.dev.vars` | 私密迁移，保持原秘密与原域名配置；先恢复再启动 |
| 本地管理员验证记录 | `.local/admin-access.json` | 私密迁移，并确认记录与当前管理员密码一致；它不是成员账号数据库 |
| 现有隧道授权 | `.local/network-access/tunnel-token.txt` | 仅在正式切换时交给新机使用；不放入公开代码或聊天 |
| 隧道程序 | `.local/tools/cloudflared.exe` | 核验后复用或安装相同受支持版本；跨系统使用对应程序 |
| 历史三维运行数据 | `.local-training/`，如果存在 | 单独归档保留，不与二维 D1/R2 合并，不启动旧三维服务替代当前站 |
| 浏览器未保存接线 | 各用户浏览器的 localStorage | 在迁移前保存到服务器或导出电路；不属于服务器目录备份 |

这些私密目录大多被 Git 忽略，因此不能只把项目上传 GitHub，再到新电脑下载，便认为数据已迁走。

`node_modules` 应按锁文件在目标电脑重新安装，不依赖复制旧机的原生二进制模块。新环境需要构建工具，使用 `npm ci --include=dev` 并保持锁文件不变；该命令的冻结依赖行为见 [npm 官方文档](https://docs.npmjs.com/cli/v11/commands/npm-ci/)。`.local/app/` 和其他构建产物可重建，不能替代业务数据。

旧机快捷方式、`.local/windows-launcher.json`、PID 文件、进程交接记录和就绪日志不作为新机当前状态使用。应在新机重新生成启动配置和快捷方式。旧日志如有保留价值放入独立归档，不据此停止新机进程。

## 先做迁移演练

1. 盘点源机版本、运行进程的实际归属、数据路径和代码状态；确认目标电脑磁盘健康、足够空间、目录不会被学校还原系统清除。尽量沿用原项目路径；盘符不同则验证全部路径与快捷方式。
2. 在约定窗口中停止外部新请求，等待正在执行的保存和上传结束，再停止本项目的所有写入进程。仅停止已确认属于本项目的进程，不按 Node 或 cloudflared 名称批量结束。没有一致性快照工具时，不能在运行中直接拷贝数据库作为可靠演练包。
3. 制作一次完整离线数据包，生成文件路径、字节数、SHA-256 和版本清单，记录数据库表数量与关键业务数据的基线。数据库检查在备份副本上进行。运行时只复制一个 SQLite 主文件可能遗漏 WAL 内容或形成不一致副本。[SQLite 官方说明](https://www.sqlite.org/howtocorrupt.html)
4. 对包含账号信息和秘密的数据包使用加密介质或加密传输。完整原始快照保留一份不启动、不修改；从副本恢复进行测试。文件校验值通过不意味着原始数据库内容健康，还需数据库完整性、外键和业务关系检查。
5. 取得一致演练包后，源机可恢复原业务。目标机只启动本地测试服务，保持生产隧道关闭；不运行会同时启动隧道的桌面总启动器。需要远程查看演练站时另用隔离的测试入口，不能接入原生产隧道。
6. 在目标新目录中恢复数据、秘密和代码，安装锁定依赖，首次启动前核对文件清单与哈希。不要先初始化空库再试图把旧数据覆盖进去。若目标目录已有数据，先归档，不能把旧快照直接覆盖混合到未知状态目录。
7. 确认端口未被其他程序占用、绑定名和数据库标识未变，再运行本地启动流程。`start:local` 会准备缺失秘密、应用迁移、构建前端、启动服务并验证管理员；因此它不是只读动作。若发现待执行的非预期数据库迁移，应先解决版本不一致。

管理员已存在时，当前初始化逻辑不会覆盖它。但若没有复制管理员验证记录，脚本可能生成不匹配的新凭据并登录失败；若 `.dev.vars` 缺失，又会生成新的秘密。这些情况应补齐原配置，不应通过清空数据库或重置所有用户来绕过。

## 如何认定数据完整

校验分为三个层次：

1. **传输完整**：首次启动前，新旧恢复包中的业务状态文件数量、大小、SHA-256 相同，证明字节复制一致。
2. **业务完整**：数据库完整性检查通过，账号 ID、角色、密码哈希、草稿内容及版本、作品快照、评测、课程与附件关联等与迁移基线一致；所有被引用的媒体对象存在且内容哈希一致。只比行数不够。
3. **实际可用**：原管理员和普通成员可登录；读取已有作品和十课图纸；在独立验收草稿上保存再回读；另一账号不能读取私有内容；浏览器真实拖线、移动缩放和重载后端点一致，课程运行正常。

服务启动或登录会改变会话、限流、时间记录等数据，因此不能要求运行后的整个数据库文件哈希仍然等于离线包。先比较离线字节，再比较业务内容，列明测试造成的预期变化。

现有 `scripts/test-persistence.mjs` 可以辅助验证指定测试草稿、PNG、PDF 和账号隔离，但它依赖既有测试凭据与证据，只覆盖一部分数据，登录退出也会修改会话状态。该脚本默认可能采用旧证据中的网址，必须明确指定目标新机测试站，不能误测仍在运行的旧公网站。`npm run test:backend` 会创建测试数据，更不能当成无写入的全量迁移证明。演练测试数据不应被误合并回正式库。

## 正式切换

演练通过后，再安排最终迁移。前面的演练副本可能已经落后于源机，不能直接用它接正式流量。

1. 提醒用户完成服务器保存或电路导出，暂停本次迁移之外的代码发布。
2. 停止旧隧道接入，收尾已有请求，停止旧站所有写入；制作最终一致性快照与校验清单。确认无人继续通过旧机 localhost 写入。
3. 停止目标演练服务，以最终快照恢复到新的干净部署目录，保留旧目录归档。再次核对版本、文件清单与业务基线。
4. 启动新机本地站并验收，准备好接入时只允许指定验收人员访问的维护入口或访问限制，暂不开放公众写入；当前仅关闭旧隧道不等于具备完整维护模式，这项能力需在正式切换前准备。
5. 确认旧生产连接器均已退出，再启用新机生产隧道。相同域名与同一隧道可继续使用，不需要为换电脑另买公网 IP。两台机器若挂同一隧道而各自使用独立数据库，请求可能到达不同副本，造成数据分叉；隧道副本不会同步数据库。[Cloudflare 副本说明](https://developers.cloudflare.com/tunnel/configuration/)
6. 完成公开 HTTPS 的指定账号验收，在新机回读一笔通过原公网域名创建的验收记录，确认请求实际到达新机。验证后解除维护限制，恢复用户写入。旧机保持关闭生产服务及隧道，不参与自动启动。
7. 新机重启后验证账号、图纸和草稿仍在，后台与隧道能够恢复；笔记本关机后，从校外手机流量等网络登录并保存回读。配置并演练定期异机备份。

首次切换可先预留 30–60 分钟维护窗口，实际按演练结果和传输速度调整；这是估算，不是零停机承诺。保留原机及最终加密快照至少 1–2 周，再按确认后的保留计划清理。

## 失败时怎样回退

新站尚未开放写入时，可以停止新站及新隧道，重新启用仍完整保留的旧站；所有步骤仍确保只有一个正式数据源。

新站已经接收用户保存后，不能直接切回迁移前旧库。应先停新站写入，备份并核对新站最新数据，再将这份完整最新状态恢复到旧机或修复新机。若新机数据本身有问题，需按具体损坏情况处理，不能承诺仅切入口就实现零丢失。

新域名 `.com` 建议在换机稳定后单独切换。同一设备、同一浏览器、同一原域名的本地恢复记录仍位于原浏览器中；新电脑或新域名不会继承其他浏览器的 localStorage。服务端已保存数据随迁移包迁走，不受用户更换终端影响。

## 后续实施应交付的工具

建议在实际迁移前补充三个可重复执行的工具：停写后的加密备份与清单生成、目标机恢复前检查、全量业务与媒体校验。当前项目有启动和部分持久化验收脚本，但还没有经实测的完整一键迁移工具，本次也未新增脚本或生成业务备份包。完成工具与迁移演练后，才能对本次数据范围给出通过或失败结论。
